# AGENTS.md — контекст для Codex

## Проект

Название: **Проект по ИАР**.

Это учебный исследовательский проект по информационной безопасности. Основная задача — создать минимальный шлюз удалённого доступа к данным по WebSocket, исследовать его поверхность атаки, затем реализовать защищённую версию с туннелированием, mTLS, авторизацией, лимитами и аудитом.

## Важный принцип

Не позиционировать проект как полноценную или сертифицированную реализацию ПТС ОРМ. Это учебный прототип, вдохновлённый требованиями проекта Указания Банка России к удалённому предоставлению данных и защищённому взаимодействию.

## Предпочтительный стек

- Python 3.12+
- FastAPI
- WebSocket
- PostgreSQL
- SQLAlchemy/asyncpg
- Docker Compose
- Nginx/Traefik или отдельный reverse proxy при необходимости
- WireGuard для туннелирования
- TLS 1.3 / mTLS с X.509 сертификатами
- pytest для интеграционных и security-тестов

Допустимо упростить стек, если это помогает уложиться в учебные сроки.

## MVP

MVP должен демонстрировать:

1. Подключение клиента к WebSocket.
2. Базовую аутентификацию.
3. Подписку на объект/пользователя.
4. Генерацию нового события в системе.
5. Доставку события подписанному клиенту.
6. Исторический запрос через `/query` или аналогичный HTTP endpoint.
7. Логирование основных событий.

## Исследуемые угрозы

Приоритетные сценарии на собственном лабораторном стенде:

1. Unauthorized WebSocket connection.
2. Broken authorization / IDOR при подписке на чужой объект.
3. Повторное использование украденного/старого токена.
4. Cross-Site WebSocket Hijacking при cookie-based auth, если применимо.
5. Connection flooding.
6. Subscription flooding.
7. Message flooding.
8. Oversized messages.
9. Malformed JSON / protocol misuse.
10. Idle connection exhaustion.
11. Slow consumer / backpressure.
12. Information disclosure через ошибки.
13. GraphQL/query abuse, если GraphQL войдёт в MVP.

Не разрабатывать инструменты для атак на чужие системы. Все проверки предназначены только для локального/собственного стенда.

## Защищённая версия

Целевые механизмы:

- WSS/TLS 1.2 или 1.3;
- mTLS и X.509 для машинной идентификации;
- VPN/WireGuard или иной защищённый туннель;
- WebSocket endpoint не должен быть доступен из публичной сети после включения tunnel-only режима;
- строгая authentication + authorization на объект/подписку;
- rate limiting;
- per-client connection limits;
- per-client subscription limits;
- max message size;
- ping/pong + idle timeout;
- backpressure handling;
- безопасная обработка ошибок;
- структурированный audit log;
- security events и метрики.

## Исследовательский формат

Для каждой выбранной угрозы использовать схему:

`Предпосылка -> сценарий -> наблюдаемый эффект -> риск -> мера защиты -> повторный тест -> результат`.

Главный результат должен быть измеримым сравнением базовой и защищённой реализации.

## Что не делать

- Не усложнять проект полной реализацией всех требований исходного регуляторного документа.
- Не реализовывать реальные функции оперативно-разыскных мероприятий.
- Не использовать реальные персональные или финансовые данные.
- Не проводить тесты против внешних систем.
- Не смешивать защищённую и намеренно слабую конфигурацию: режимы должны быть разделены и явно документированы.
